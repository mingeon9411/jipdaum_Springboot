
⭐ 아이디/비밀번호 찾기(보안질문 기반) 실제 구현 및 배포 (2026-09-06)

✅ 로그인 화면 "아이디 찾기"/"비밀번호 찾기"가 완전 목업이었던 것을 발견해 실제 기능으로 구현

➡️ 조사 결과: Team-DaumAna `FindAccount.jsx`는 이메일 형식만 검사하고 `setSubmitted(true)`로
   성공 문구만 띄우는 클라이언트 목업 — API 호출 자체가 없었음. Django `Users` 앱은
   `views.py`/`urls.py`가 아예 없고(관리자 모델 전용), Spring `UserAuthService`에도
   대응 메서드가 전혀 없어 백엔드가 원래 존재하지 않던 기능이었음
➡️ 보안질문/답변 개념도 코드·DB(`JIPDAUM_USER`) 어디에도 없어서 처음부터 설계: 고정
   질문 5개 중 선택(자유 입력 아님), 비밀번호 찾기는 본인확인 통과 후 그 자리에서
   새 비밀번호 직접 입력(임시비번 이메일 발송 아님), 기존회원 안내는 로그인 성공 후
   화면 표시하되 건너뛰기 가능 — 세 가지 모두 설계 확정 전 사용자에게 직접 확인받음

✅ 스키마 변경 (Django 마이그레이션이 소유, 공유 MySQL `JIPDAUM_USER`)

➡️ Team-DaumAna `backend/Users/migrations/0003_user_security_question_answer.py`로
   `security_question`(질문 텍스트)/`security_answer`(BCrypt 해시, 평문 금지) nullable
   컬럼 2개 추가 — 기존 회원은 자동 NULL로 남아 "미설정" 판별 기준이 됨
➡️ 로컬 검증 전 `python manage.py migrate`로 직접 적용해 컬럼 생성 확인. 운영 배포는
   Django `entrypoint.sh`가 컨테이너 기동 시 `migrate --noinput`을 자동 실행하므로
   별도 조치 없이 이번 배포에 바로 반영됨

✅ 백엔드(jipdaum_Springboot) 신규 엔드포인트 6개 + 기존 인프라 재사용

➡️ `GET /api/users/security-question`, `POST /api/users/find-id/send-code`,
   `/find-id/verify`, `/find-password/verify`, `/find-password/reset`(이상 공개),
   `PATCH /api/users/security-qa`(로그인 사용자 설정/변경) 추가
➡️ 이메일 발송은 `UserAuthService.sendEmailOtp`(JavaMailSender+`EmailOtp` 엔티티,
   네이버 SMTP)를 그대로 재사용 — 새 메일 발송 경로를 따로 안 만듦
➡️ 비밀번호 재설정 본인확인 토큰은 새 테이블 없이 `JwtTokenProvider`에 `TYPE_PW_RESET`
   타입(TTL 10분)을 추가해 기존 JWT 인프라 재사용
➡️ `SecurityConfig.authorizeHttpRequests`에서 새 공개 엔드포인트를 기존 permitAll
   목록에 추가 — 안 넣으면 `"/api/admin/**", "/api/users/**").hasRole("ADMIN")`
   규칙에 먼저 걸려 비로그인 사용자가 전부 403을 받는 걸 미리 확인하고 반영

✅ 실제 디버깅으로 검수 — curl 전 구간 + 브라우저 실행 확인, 버그 1건 발견/수정

➡️ curl로 회원가입(보안질문 포함)→아이디 찾기→비밀번호 찾기→새 비밀번호 로그인까지
   실제 실행, 오답/틀린 닉네임/가짜 토큰/미가입 이메일/잘못된 보안질문 등 실패
   케이스도 전부 확인(계정 존재 여부 과다 노출 안 하는 것까지 확인)
➡️ 로컬 브라우저(5173/8081)로 두 플로우 전부 끝까지 완주해 실제 새 비밀번호로 로그인
   성공하는 것까지 확인 — 화면에서 성공 문구만 뜨는 게 아니라 실제 DB 반영을 검증
➡️ 검수 중 `verifyFindId`가 보안답 확인보다 OTP 소모를 먼저 하는 순서 문제를 발견 —
   순서를 답 확인 → OTP 소모로 바꿔 수정(`@Transactional` 롤백 덕에 실제 데이터
   손상은 없었던 것으로 확인됐지만, 순서 자체는 더 명확하게 고침)
➡️ 다른 세션이 작업 중이던 `UserAuthServiceTest.java`가 `RegisterRequest` 필드 추가로
   컴파일이 깨진 것을 발견 — 그 파일의 다른 내용은 손대지 않고 생성자 호출부만
   기계적으로 맞춰 수정. 새 로직 검증용 단위테스트는 별도 파일
   (`UserAuthServiceSecurityQaTest.java`)로 4개 추가, 전체 39개 테스트 통과
