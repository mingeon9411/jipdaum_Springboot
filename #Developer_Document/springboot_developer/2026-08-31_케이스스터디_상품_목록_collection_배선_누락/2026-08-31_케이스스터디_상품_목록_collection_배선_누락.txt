================================================================================
1. Troubleshooting — 증상, 원인, 해결 과정
================================================================================

증상: 프론트(Team-DaumAna) 저장소에서 메인/한국관 상품 카탈로그 연동 구조를 진단하다가,
"진열(collection)별로 상품을 나눠 보여줄 방법이 없다"는 게 확인됨.

원인: 6일 전(2026-08-20, df3c8bf)에 챗봇 상품 검색(ProductSearchTool)을 위해
ProductRepository에 collection 조건이 붙은 파생 쿼리 4개(findByCollection,
findByCategoryIdAndCollection, searchByPatternAndCollection,
searchByPatternAndCategoryAndCollection)와 ProductService.getProducts(search, categoryId,
collection) 3-인자 오버로드가 이미 구현돼 있었다. 그런데 공개 REST 엔드포인트인
ProductController.listProducts는 여전히 (search, category) 2개 파라미터만 받아 기존
2-인자 오버로드만 호출하고 있어서, 이미 존재하는 collection 필터링 기능에 프론트가
도달할 방법 자체가 없었다 — 로직은 있는데 마지막 배선(컨트롤러 파라미터) 하나가 안
이어진 상태.

해결 (51ff149):
➡️ ProductController.listProducts에 @RequestParam(required=false) String collection
   추가, productService.getProducts(search, category, collection)로 이미 있던 3-인자
   오버로드를 그대로 호출하도록 변경. diff는 컨트롤러 한 파일 +6/-2줄 — 리포지토리/서비스
   쪽 로직은 8/20에 이미 완성돼 있었으므로 이번 수정에서 새로 짠 쿼리는 0개.
➡️ 하위 호환: collection을 안 넘기면 기존과 동일하게 전체 상품을 반환.
➡️ 프론트 실제 화면 반영은 보류: JIPDAUM_PRODUCT의 main 컬렉션 시드 데이터가 현재 프론트
   상품 라인업과 무관한 옛 데이터라, 그대로 merge하면 화면에 엉뚱한 상품이 뜰 위험이 있어
   조회만 가능하게 API만 열어두고 프론트 연동은 다음으로 미룸(korean_hall 컬렉션은 이름/
   가격이 이미 프론트와 1:1 일치해 프론트 로컬 id만 DB 기준으로 재구성 — Team-DaumAna
   저장소 쪽 작업, 이 저장소 범위 밖이라 이후 상태는 확인하지 않음).

부수적으로 발견된 문제 (같은 커밋 안에서): 이 변경은 원래 별도 커밋으로 나가려 했으나,
같은 워킹트리에서 동시에 진행 중이던 SMTP 진단/수정 세션이 먼저 커밋할 때 같이 묶여
51ff149("이메일 SMTP 환경변수 주입 추가")라는, 실제 변경 내용과 안 맞는 커밋 메시지로
커밋·푸시·배포됐다. 코드 자체는 정상 반영됐지만, 커밋 히스토리만 보고 이 변경을 찾으려는
사람은 못 찾는다.

2. Trade-off — 왜 이 방식을 선택했나
================================================================================

[선택 1] collection 필터를 프론트에 바로 merge  vs  API만 먼저 열고 프론트 연동은 보류
  → 후자를 선택. main 컬렉션 시드 데이터가 옛 것이라 그대로 merge하면 프론트 화면에
    실제 판매 중이 아닌 상품이 뜰 위험이 있다. "기능은 있지만 데이터가 아직 안 맞다"와
    "기능 자체가 없다"를 구분해, 데이터 정합성 문제를 API 노출과 분리해서 나중에
    별도로 해결하기로 함.

[선택 2] 기존 2-인자 getProducts(search, categoryId) 시그니처를 지우고 3-인자로 통일
         vs  오버로드로 남겨 기존 시그니처를 그대로 유지
  → 후자를 선택 — 당시엔 이 2-인자 메서드를 다른 곳에서도 쓰고 있을 가능성을 배제하지
    않고 하위 호환을 우선한 합리적 판단이었다. 다만 이번 케이스 스터디를 쓰며 코드를
    다시 훑어보니, 지금 이 2-인자 오버로드를 실제로 호출하는 곳은 (자기 자신을 통한
    위임 말고는) 저장소 전체에 없다 — 즉 지금은 죽은 코드가 됐다(3장 Metrics, 4장
    Post-mortem 참고). 선택 자체는 그 시점엔 맞았지만, 그 이후 상황이 바뀌었는데
    아무도 다시 확인하지 않은 경우다.

[선택 3] categoryId/collection 조합마다 별도 리포지토리 메서드를 계속 늘리는 if/else
         분기(현재 방식)  vs  Specification/QueryDSL 같은 동적 쿼리 빌더로 전환
  → 아직은 전자를 유지. getProducts 안의 분기는 지금 "검색어 유무 × categoryId 유무 ×
    collection 유무" 조합으로 최대 8갈래인데, 필터가 딱 2개뿐이라 파생 쿼리 이름 몇 개로
    감당 가능한 크기다. 필터 조건이 하나만 더 늘면(예: 가격대, 재고 상태) 분기가 조합
    폭발을 일으키므로 그 시점이 Specification으로 갈아탈 타이밍 — 지금 미리 그 구조를
    만드는 건 필요 이상의 추상화(YAGNI).

4. Post-mortem — 재발 방지로 실제 반영된 것 / 아직 안 된 것
================================================================================

실제로 반영됨:
➡️ 코드: 컨트롤러에 파라미터를 배선해 이미 만들어져 있던 기능을 실제로 쓸 수 있게 함,
   하위 호환 유지.
➡️ 안전장치: 시드 데이터 정합성 문제를 인지하고 프론트 병합을 명시적으로 보류 — "된다고
   보이지만 데이터가 틀렸다"는 더 나쁜 상태를 피함.

➡️ 코드 (2026-08-31 추가): 죽은 2-인자 getProducts(search, categoryId) 오버로드를
   삭제 — CLAUDE.md 자체 검수 체크리스트의 "데드 코드" 항목이 지적하는 그 상태를
   실제로 정리. 남아있던 3-인자 메서드의 자바독도 더 이상 존재하지 않는 2-인자
   오버로드를 언급하던 부분을 바로잡음. mvnw test 33개 전부 통과로 회귀 없음 확인.

⚠️ 아직 안 됨 (이 케이스 스터디를 쓰며 코드로 직접 확인, 수정은 하지 않음 — 사용자 판단 필요):
➡️ 테스트 부재: collection 필터(공개 API 경로든 챗봇 경로든)를 겨냥한 테스트가 0개다.
   앞의 두 케이스 스터디(302 리다이렉트, 챗봇 지연)와 같은 패턴 — 이 저장소는 "코드
   리뷰로 잡은 것을 테스트로 고정하는 습관"이 아직 이 영역까지 안 퍼져 있다.
➡️ 커밋 히스토리 오염: 51ff149라는 커밋 메시지만 보고는 이 collection 변경을 찾을 수
   없다. 이미 push/배포된 히스토리라 되돌리진 않되, "동시에 여러 작업을 같은 워킹트리에서
   진행할 때는 커밋 전에 diff를 기능 단위로 나눠서 커밋한다"는 규칙이 아직 CLAUDE.md
   워크플로우 섹션에 없다 — 이번 발견을 계기로 추가할지는 사용자 판단.
➡️ 프론트 실제 반영 상태 미확인: Team-DaumAna 저장소는 이 케이스 스터디의 확인 범위
   밖이라, "8/26 시점엔 보류였다"는 것만 근거가 있고 그 이후 실제로 merge됐는지는
   이 문서에서 다루지 않는다.
