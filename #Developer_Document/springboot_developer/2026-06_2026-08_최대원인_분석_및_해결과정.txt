--------------------------------------------------------------------------------
1-0. 왜 이 구조가 생겼나 (배경)
--------------------------------------------------------------------------------

➡️ src/main/resources/application.yml에는 DB 비밀번호, JWT secret, SMTP 자격증명,
   OAuth client secret, hCaptcha secret 등 민감정보가 그대로 들어간다. 이걸 git에 커밋하면
   저장소를 보는 누구나 프로덕션 DB/메일 계정에 접근할 수 있게 되므로 .gitignore 대상으로
   뺀 것 자체는 정상적인 보안 판단이었다(CLAUDE.md에도 명시).
➡️ 문제는 그 대가로 "로컬 PC의 application.yml"과 "EC2 서버의
   /opt/jipdaum/config/application.yml"이 파일 시스템상 완전히 별개의 두 파일이 됐다는
   것이다. 코드(예: SecurityConfig의 @Value("${app.xxx}"))가 새 설정 키를 요구하게
   바뀌어도, 그 키를 EC2 파일에 반영하는 절차가 자동화돼 있지 않았다.
➡️ 배포는 .github/workflows/docker-publish.yml이 담당하는데, EC2에서 실행하는
   `docker run`은 fire-and-forget이다 — 컨테이너가 뜨자마자 크래시해도 GitHub Actions
   워크플로 자체는 "명령을 실행했다"는 사실만 보고 success로 끝난다. 즉 배포 파이프라인에
   "컨테이너가 실제로 정상 기동했는가"를 확인하는 헬스체크가 없었다.
➡️ 이 두 가지(① 설정 동기화 수단 부재 ② 배포 후 검증 부재)가 겹치면서, "로컬에서는 되는데
   프로덕션에서만 조용히 깨지는" 사고가 반복될 조건이 갖춰져 있었다.

1-1. 사건 ①: hCaptcha 실패 원인이 로그에 안 남음 (발견 2026-08-23, 로깅 보강 커밋 b03e9d0)
--------------------------------------------------------------------------------

증상: 프로덕션에서 회원가입/로그인 시 "보안 인증에 실패했습니다"가 뜨는데 서버 로그에는
아무 단서가 없었음.

진단 과정:
➡️ HCaptchaService.verify()를 열어보니, hCaptcha siteverify API 호출 자체가 실패
   (네트워크 오류/타임아웃)한 경우에만 로그를 남기고 있었다. hCaptcha가 정상적으로
   200 응답하면서 그 안에 success:false를 담아 보내는 경우(토큰 재사용, 토큰 만료,
   sitekey/secret 불일치, 등록 도메인 불일치 등)는 애초에 로그를 남기는 코드 경로가 없었다.
➡️ 즉 "설정값(secret/도메인)이 로컬과 프로덕션에서 다를 수 있다"는 그 자체가 원인 후보인데,
   그걸 확인할 관측 수단이 없어서 어느 쪽인지 구분이 불가능한 상태였다.

해결:
➡️ success:false 응답을 받으면 hCaptcha가 함께 내려주는 error-codes/hostname을 그대로
   로그에 남기도록 수정, 네트워크 실패 로그에도 어떤 verify-url을 호출했는지 같이 남겨
   "EC2 아웃바운드 네트워크 문제인지 / 설정값 불일치인지"를 다음 재현 시 구분할 수 있게 함.
➡️ 이 시점에는 근본 원인(정확히 어떤 값이 프로덕션에서 다른지)까지는 확정하지 못했고,
   "다음에 같은 증상이 재현되면 원인이 로그에 잡히도록" 관측 가능성부터 확보하는 데 그쳤다
   — 바로 아래 사건 ②③이 결국 같은 유형(로컬/프로덕션 설정 불일치)임을 뒷받침한다.

1-2. 사건 ②: 프로덕션 회원가입 메일이 실제로 안 나감 (진단/수정 2026-08-26, 커밋 51ff149)
--------------------------------------------------------------------------------

증상: 실사용자 가입/이메일 OTP 발송 플로우에서 메일이 실제로 발송되지 않음이 확인됨.

진단 과정 (단계별):
➡️ 1단계 — 로컬 설정 상태부터 재확인: application.yml.example은 smtp.gmail.com + 더미
   값이지만, 실제 로컬 application.yml은 smtp.naver.com +
   ${EMAIL_HOST_USER:}/${EMAIL_HOST_PASSWORD:}로 Windows 사용자 환경변수를 참조하도록
   돼 있었고, 그 환경변수엔 실제 네이버 계정 값이 이미 등록돼 있어 로컬은 정상 발송
   가능한 상태였다. (CLAUDE.md에 남아있던 "더미라 실발송 안 됨"이라는 옛 기술이 이미
   낡은 정보였음을 이 과정에서 확인/정정함.)
➡️ 2단계 — "로컬은 되는데 프로덕션만 안 된다"로 범위를 좁힘 → 배포 파이프라인 점검.
   .github/workflows/docker-publish.yml의 EC2 배포 스텝을 열어보니, `docker run`이
   /opt/jipdaum/config/application.yml 파일만 컨테이너에 마운트할 뿐, EMAIL_HOST_USER/
   EMAIL_HOST_PASSWORD 같은 환경변수는 전혀 주입하지 않고 있었다.
➡️ 3단계 — 근본 원인 확정: application.yml의 ${EMAIL_HOST_USER:} placeholder는 뒤에
   콜론이 있어 "환경변수가 없으면 빈 문자열"로 기본값 처리된다. 로컬 PC는 OS 레벨
   환경변수로 채워지지만, EC2 컨테이너에는 그 환경변수 자체가 없으니 항상 빈 문자열로
   풀렸고, 그 결과 네이버 SMTP 인증(아이디/비번 빈 값)이 항상 실패하는 구조였다.
   → 예전부터 계속 실패하고 있었는데, 실사용자 신고가 나올 때까지 아무도 몰랐던 것.

해결:
➡️ docker run에 -e EMAIL_HOST_USER / -e EMAIL_HOST_PASSWORD / -e EMAIL_FROM_ADDRESS
   3개 플래그를 추가하고, 값은 EC2 파일에 평문으로 박아두지 않고 GitHub Secrets를
   워크플로에서 참조하도록 함(시크릿을 배포 "시점"에만 주입, 저장소/서버 파일엔 안 남김).
➡️ 이 플래그가 동작하려면 GitHub 저장소 Settings → Secrets and variables → Actions에
   같은 이름의 Secret 3개가 실제 값으로 등록돼 있어야 한다 — 코드만으로는 안 끝나는
   부분이라 사용자에게 등록을 요청했고, 등록 완료 후 workflow_dispatch로 수동
   재배포(build-and-push/deploy 둘 다 success)까지 확인해서 실제로 반영됐음을 검증함.
➡️ 부수적으로, HANDOFF_AUTH_SCOPE.md(2026-07-14 작성)에 "이메일 OTP는 Django에 남긴다"고
   적혀 있던 게 이후(a946b2c, 7/20) Spring UserAuthService로 실제 포팅되면서 낡은
   정보가 됐다는 것도 이번 진단 중에 같이 확인 — CLAUDE.md에 "이 문서는 옛 스냅샷이니
   기능 분담은 코드 기준으로 판단할 것"이라고 명시해 다음 사람이 같은 삽질을 안 하게 기록함.

1-3. 사건 ③: 새 설정 키 하나 추가했다가 프로덕션 API 전체가 502로 멎음
      (발생/진단/수정 2026-08-28, 커밋 26bac46 → e24307d)
--------------------------------------------------------------------------------

이 사건이 세 사건 중 가장 심각하다 — "설정 드리프트"라는 같은 원인이, 이번엔 일부
기능(메일)이 아니라 서비스 전체를 멈춰 세웠다.

경위:
➡️ CORS 허용 origin을 OAuth2 리다이렉트용 app.frontend-url(값 하나 고정)과 분리해,
   로컬 dev(nip.io)와 배포(jipdaum.life)를 동시에 허용하려고 app.cors-allowed-origins
   (콤마 구분 목록)이라는 새 설정 키를 SecurityConfig에 추가함(26bac46). 로컬에서는
   해당 키를 넣은 application.yml로 curl 테스트까지 마치고 정상 동작을 확인한 뒤 배포.
➡️ 그런데 EC2의 application.yml은 이 저장소 파일과 무관한 별도 파일(gitignore 대상)이라,
   방금 코드에 추가한 app.cors-allowed-origins 키가 아직 없는 상태 그대로였다.
   @Value("${app.cors-allowed-origins}")에 기본값을 안 줬기 때문에, 이 키가 없으면
   Spring이 컨텍스트 초기화 자체에 실패한다.
➡️ 컨테이너가 뜨자마자 죽었지만, 위 1-0에서 설명한 대로 `docker run`이 fire-and-forget이라
   GitHub Actions는 이번에도 success로 표시됐다. 즉 "배포는 성공했다"는 신호를 받았는데
   실제로는 프로덕션 API 전체가 502를 반환하는 상태가 그대로 방치될 뻔한 상황이었다
   — 2026-08-28에 실제로 이 상태가 확인됨.

진단:
➡️ 502 증상 → 최근 배포(26bac46)에서 새로 추가된 설정 키를 의심 → EC2 application.yml에
   해당 키가 없다는 것과, 그 키에 해당하는 @Value에 기본값이 없어 컨텍스트 초기화가
   실패한다는 것을 코드 레벨에서 바로 특정. 사건 ②를 겪은 직후라 "새 설정 키 = EC2 파일엔
   없을 수 있다"는 가설을 곧바로 떠올릴 수 있었다는 점에서, 사건 ②의 진단 경험이 사건 ③의
   원인 특정 속도를 크게 앞당겼다.

해결:
➡️ app.cors-allowed-origins가 없으면 기존 app.frontend-url 값으로 자동 폴백하도록
   중첩 플레이스홀더 기본값(${app.cors-allowed-origins:${app.frontend-url}})을 추가.
   즉 "새 키가 없어도 최소한 기존 동작으로는 뜬다"는 안전장치를 코드 레벨에 심음.
➡️ 로컬에서 실제로 그 프로퍼티를 뺀 yml로 기동 테스트를 다시 돌려 "정상 기동 +
   frontend-url로 폴백"까지 확인한 뒤 배포.

1-4. 같은 매커니즘이 프론트엔드(별도 저장소)에서도 재현됨 — 참고
--------------------------------------------------------------------------------

➡️ 2026-08-23, Team-DaumAna(Cloudflare Pages)에서도 VITE_HCAPTCHA_SITE_KEY가 배포
   환경변수에 등록되지 않아 "Missing sitekey" 에러가 났고, 값을 등록해도 Vite가 빌드
   시점에 값을 번들에 굳히는 방식이라 재배포 없이는 반영이 안 됐다. 게다가 Cloudflare
   Pages의 기본 Node 버전(18.x)이 vite 7 요구사항(>=20.19)에 안 맞아 그 이전부터도
   빌드 자체가 조용히 계속 실패하고 있었을 가능성이 발견됨.
➡️ 이건 이 저장소(jipdaum_Springboot)의 문제는 아니지만, "배포 환경의 설정/버전이
   저장소 코드와 별도로 관리되고, 실패해도 파이프라인이 소리 없이 넘어간다"는 정확히
   같은 매커니즘이 프론트에서도 똑같이 사고를 냈다는 점에서, 이번 3개월의 최대 원인이
   이 프로젝트 한정의 우연이 아니라 이 스택 전반의 구조적 사각지대였음을 보여준다.

1-6. 재발 방지책 — 실제로 반영된 것 / 앞으로 필요한 것
--------------------------------------------------------------------------------

이미 반영된 것:
➡️ 새 @Value 설정 키를 추가할 때는 가능하면 기본값(또는 기존 키로의 폴백)을 같이
   넣는다는 패턴을 e24307d에서 실제로 적용함.

⭐ 2장. 두 번째로 큰 원인 — Spring Security 302 리다이렉트가 axios의 JSON 기대와 충돌
================================================================================

이 원인은 설정 드리프트와 달리 "코드 안에" 있는 구조적 함정이고, 3주 간격으로 두 번
서로 다른 경로에서 재발했다는 점에서 두 번째로 크게 꼽는다.

매커니즘: Spring Security의 oauth2Login()이 기본 제공하는 미인증 요청 처리기는
클라이언트에게 302로 /login을 돌려준다. Boot의 기본 에러 처리도 처리되지 않은 예외를
/error로 "포워드"하는데, 이 포워드된 요청 역시 SecurityConfig의
anyRequest().authenticated() 규칙에 걸려 다시 /login으로 302가 나간다. 프론트는 axios로
호출하는데, axios/fetch는 302를 그냥 따라가서 로그인 페이지의 HTML을 200 OK로 받아버리고,
JSON을 기대하던 프론트 코드가 그 HTML을 파싱하려다 크래시한다(예: 배열 아닌 값에 .filter()).

--------------------------------------------------------------------------------
2-1. 1차 발견/수정 (2026-08-07, 커밋 2b2d579)
--------------------------------------------------------------------------------

➡️ 증상: 토큰 만료 후 마이페이지 진입 시 정상적인 401 대신 로그인 HTML을 200으로 받아
   프론트가 크래시.
➡️ 원인 특정: oauth2Login()의 기본 AuthenticationEntryPoint가 /login으로 302를 보낸다는
   것.
➡️ 조치: RestAuthenticationEntryPoint를 새로 만들어 defaultAuthenticationEntryPointFor로
   /api/** 경로에만 스코프를 좁혀 적용 — non-API 경로(실제 OAuth2 로그인 플로우)는
   기존 302 동작을 그대로 두고, /api/**만 JSON 401을 반환하도록 함.
➡️ 이 시점의 수정은 "인증이 아예 안 된 요청"이라는 한 가지 경로만 막은 것이었다 —
   "인증은 됐지만 요청 검증(@Valid)에서 예외가 난 경우"나 "그 외 처리되지 않은 모든
   예외"가 여전히 Boot 기본 /error 포워드 → 같은 302 경로를 타는 건 이때 안 잡혔다.

--------------------------------------------------------------------------------
2-2. 재발 (2026-08-27, 커밋 90b0ef2) — 왜 3주 뒤 다시 터졌나
--------------------------------------------------------------------------------

➡️ 발견 경위: 백엔드 변경분을 실제로 디버깅하며 검수하던 중, GlobalExceptionHandler를
   들여다보니 ResponseStatusException류는 처리하고 있었지만
   MethodArgumentNotValidException(@Valid 검증 실패)과 그 밖의 모든 미처리
   Exception은 핸들러가 아예 없다는 게 확인됨 — 코드 안에 이미 "여기 안 걸리면
   /login으로 302 나간다"고 설명하는 주석까지 있었는데, 정작 그 주석이 경고하는
   케이스 자체는 방치돼 있던 상황.
➡️ 영향 범위 확인: grep으로 @Valid를 쓰는 컨트롤러 메서드를 전수 확인 — 회원가입/
   로그인/장바구니/주문/결제 등 19개 엔드포인트가 이 미처리 경로에 노출돼 있었다.
   즉 이 19개 엔드포인트 중 어느 하나라도 유효성 검증에서 걸리면(빈 값, 형식 오류 등)
   프론트가 깔끔한 필드 에러 대신 크래시를 겪는 상태가 2b2d579(8/7) 이후 3주 가까이
   방치돼 있었던 셈.
➡️ 재발 이유: 1차 수정이 "미인증(anonymous) 요청"이라는 한 가지 진입점만 막았을 뿐,
   "인증된 사용자의 요청이 컨트롤러 안에서 예외를 던지는" 케이스는 완전히 다른
   코드 경로(GlobalExceptionHandler)를 타는데 그건 손대지 않았기 때문 — 같은 증상
   (axios가 HTML을 받아 크래시)이 서로 다른 원인 경로 두 개에서 나올 수 있다는 걸
   1차 수정 때는 일반화하지 못했다.

해결:
➡️ GlobalExceptionHandler에 MethodArgumentNotValidException 핸들러를 추가해
   {"<field>": message} 형태로 응답(FieldValidationException과 동일한 관례,
   Register.jsx가 실제로 기대하는 포맷에 맞춤).
➡️ 그 외 모든 미처리 Exception을 잡는 핸들러도 추가해 500 JSON을 반환하고,
   스택트레이스는 응답에 노출하지 않고 서버 로그에만 남기도록 함.
➡️ 재발 방지를 위해 이번엔 "이 함수 하나 고치기"에서 그치지 않고, CLAUDE.md에
   "백엔드 변경 시 자체 검수 체크리스트"를 신설 — 새 예외 타입을 던지는 코드를 추가할
   때마다 GlobalExceptionHandler에 걸리는지를 매번 확인하도록 프로세스화함(코드 수정
   1건 → 재발 시 프로세스 개선으로 대응 범위를 넓힌 사례).
