================================================================================
1. Troubleshooting — 증상, 원인, 해결 과정
================================================================================

아키텍처: POST /api/shop/chat은 GeminiClient.generate()가 Gemini의 functionCall 루프를
최대 MAX_TOOL_CALL_ROUNDS번 돈다. 한 라운드 = Gemini API 호출 1회(대부분의 지연은 여기서
발생, 도구 실행 자체는 로컬 DB 조회라 수 ms 수준). 모델이 functionCall 없이 텍스트를
반환하면 그 라운드에서 즉시 종료, 아니면 도구(search_products / get_product_detail)를
실행해 결과를 히스토리에 얹고 다음 라운드로 넘어간다.

증상: "소파 추천해줘" 같은 일반 추천 질문 한 번에 상품별 상세조회(get_product_detail)를
반복 호출하면서 당시 상한(MAX_TOOL_CALL_ROUNDS=4)을 꽉 채워, 응답까지 30~60초가 걸림.

원인: search_products가 이미 이름/브랜드/가격/카테고리를 응답에 담아 오는데도, 시스템
프롬프트에 "결과가 충분하면 그것만으로 답하라"는 지침이 없어 모델이 추천 후보 상품마다
get_product_detail을 추가로 호출했다. 라운드 하나가 곧 Gemini 왕복 1회이므로, 상품 3~4개를
상세조회하면 그것만으로 상한(4라운드)을 다 쓴다.

해결 (1fe06e5):
➡️ 프롬프트에 "search_products 결과만으로 답변하고, 고객이 특정 상품 하나를 콕 집어
   '더 자세히'를 요청한 경우에만 get_product_detail을 쓰라. search_products도 한 질문에
   한 번이면 충분하다"는 지침 추가 — 정상 흐름이면 검색 1라운드 + 답변 1라운드로 종료.
➡️ MAX_TOOL_CALL_ROUNDS를 4 → 3으로 축소. 2까지 낮추면 "상품 상세를 콕 집어 질문"하는
   정당한 케이스(검색+상세조회+답변 = 3라운드)가 한도 초과로 폴백돼버리므로, 에러 없이
   갈 수 있는 최소치로 3을 남김.

참고 (같은 날 발견된 별개 문제, a17172c): Gemini가 tools를 포함한 큰 요청에서 실제로는
유효한 JSON을 주면서도 Content-Type을 application/octet-stream으로 잘못 내려주는 경우가
있어, Content-Type 기반으로 컨버터를 고르는 .body(Map.class)가 계속 실패했다. 무료
할당량 소진(429)에 가려져 있다가 유료 티어 전환 후 실제 200 응답을 받으면서 드러남.
.body(String.class)로 받아 ObjectMapper로 직접 파싱하도록 우회 — 지연 문제와는 별개
원인이지만, 같은 GeminiClient 안정화 세션에서 함께 고쳐짐.

2. Trade-off — 왜 이 방식을 선택했나
================================================================================

[선택 1] 도구를 코드로 강제 제한(예: get_product_detail 자체를 비활성화)  vs
         프롬프트 지시로 모델이 스스로 아끼게 유도
  → 후자를 선택. 도구를 아예 막으면 "이 소파 소재가 뭐예요?" 같이 정말 상세조회가
    필요한 정당한 질문까지 못 받게 된다. 프롬프트 지시는 모델이 지키지 않을 수도 있는
    soft guarantee지만, 기능을 죽이지 않으면서 일반적인 경우의 낭비만 줄인다.

[선택 2] MAX_TOOL_CALL_ROUNDS를 2로 낮춰 지연 상한을 확실히 보장  vs  3으로 유지
  → 후자를 선택. 2로 낮추면 "상품 상세를 콕 집어 질문"하는 케이스(검색 1 + 상세조회 1 +
    답변 1 = 3라운드)가 정상적인 상황에서도 한도를 넘겨 규칙 기반 폴백으로 떨어진다.
    "항상 빠르지만 가끔 대답을 못 한다"보다 "대부분 빠르고 드문 케이스만 한 라운드 더
    쓴다"를 택함 — 지연 상한을 1라운드 더 여유 있게 잡는 대신 정답률을 지켰다.

[선택 3] 라운드 한도를 없애고 프롬프트 지시만 신뢰  vs  프롬프트 지시 + 하드 라운드 캡
         동시 적용
  → 후자를 선택. 프롬프트는 모델이 매번 똑같이 따른다는 보장이 없는 soft guidance이므로,
    프롬프트가 안 먹힌 경우를 대비해 코드 레벨의 하드 상한(3)을 안전망으로 남겼다.
    한도를 넘기면 예외를 던지지 않고 Optional.empty() → 상위 ChatService가 규칙 기반
    응답으로 조용히 폴백(기존 아키텍처의 graceful degradation 원칙과 동일).

================================================================================
4. Post-mortem — 재발 방지로 실제 반영된 것 / 아직 안 된 것
================================================================================

실제로 반영됨:
➡️ 코드: 프롬프트 지시 + MAX_TOOL_CALL_ROUNDS 4→3 두 겹으로 적용(2장 선택 3).
➡️ 문서: GeminiClient.java에 "왜 3인지, 2로 낮추면 어떤 케이스가 깨지는지"를 설명하는
   주석을 코드에 직접 남김 — 다음에 라운드 상한을 만질 사람이 같은 실수(2로 낮췄다가
   상세조회 케이스를 깨뜨리는 것)를 반복하지 않도록 함.
➡️ 아키텍처: 라운드 초과 시 예외가 아니라 규칙 기반 폴백으로 떨어지는 기존 원칙을
   그대로 유지 — 프롬프트가 실패하는 최악의 경우에도 사용자는 크래시가 아니라 정직한
   대체 응답을 받는다.
➡️ 회귀 테스트 (2026-08-31 추가): GeminiClientTest(2개) — MockRestServiceServer로 실제
   Gemini 호출 없이, "functionCall 없이 텍스트만 오면 1라운드에서 끝난다"와 "functionCall이
   라운드 상한(3)을 넘기면 예외 없이 폴백(empty)한다"를 고정. 코드가 실제로 보장하는
   두 가지 — 최대 라운드에서 멈춘다는 것과 즉시 종료 조건 — 를 이제 테스트가 지킨다.
   단, 이건 "프롬프트를 안 지켜도 시스템이 안전하게 멈춘다"는 하드 안전망만 검증한다 —
   "프롬프트 지시 덕분에 정상 흐름이 실제로 2라운드로 끝난다"는 모델의 실제 행동에
   대한 주장이라 아래 갭으로 남는다.

⚠️ 아직 안 됨 (이 케이스 스터디를 쓰며 코드로 직접 확인, 수정은 하지 않음 — 사용자 판단 필요):
➡️ 수정 후 실제 응답 시간 재측정/로깅 부재: "30~60초"는 수정 전 증상 기록일 뿐, 수정
   후 몇 초로 줄었는지 실측한 값이 어디에도 없다. 라운드 수가 줄었다는 것과 실제 체감
   지연이 줄었다는 것은 다른 주장이다 — GeminiClient.generate()에 라운드 수/총 소요시간을
   로그로 남기는 게 가장 싼 확인 수단인데 아직 없다.
➡️ 폴백 발생 빈도 관측 부재: 라운드 상한에 걸려 규칙 기반 응답으로 내려간 경우가 실제로
   얼마나 자주 발생하는지 세는 수단(카운터/메트릭)이 없다 — 지금은 로그(log.warn)에만
   남고 집계되지 않아, "3이 충분한 여유인지"를 사후에 확인할 방법이 없다.
