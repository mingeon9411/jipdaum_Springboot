================================================================================
1. Troubleshooting — 증상, 원인, 해결 과정
================================================================================

증상 (공통): 프론트(axios)가 JSON을 기대하는 API 호출에서, 인증/검증에 실패하면 정상적인
401/400 JSON 대신 로그인 페이지의 HTML을 200 OK로 받아버려 크래시 (예: 배열이 아닌 값에
.filter() 호출). 토큰 만료 후 마이페이지 진입, 회원가입 폼 검증 실패 등에서 재현.

메커니즘: Spring Security의 oauth2Login()이 등록하는 기본 미인증 처리기는 /login으로
302를 응답한다. Boot는 처리되지 않은 예외를 기본적으로 /error로 "포워드"하는데, 이 포워드된
요청도 SecurityConfig의 anyRequest().authenticated() 규칙에 다시 걸려 같은 /login 302를
받는다. axios/fetch는 302를 그대로 따라가므로, JSON을 기대하던 호출부가 로그인 HTML을
파싱하려다 죽는다.

--- 1차 (2026-08-07, 2b2d579) ---
원인 특정: "인증이 아예 안 된 요청" 하나의 진입점 — oauth2Login()의 기본
AuthenticationEntryPoint.
해결: RestAuthenticationEntryPoint(신규)를 만들어 SecurityConfig에
defaultAuthenticationEntryPointFor(restAuthenticationEntryPoint,
new AntPathRequestMatcher("/api/**"))로 등록. /api/**만 401 JSON을 강제하고,
oauth2Login() 자신의 진입점(비-API 경로, 실제 OAuth2 로그인 플로우)은 손대지 않음.
한계 (이때는 인지 못함): 이건 "인증되지 않은 요청" 경로 하나만 막은 것 — "인증은 됐지만
컨트롤러 안에서 예외(@Valid 실패, NPE 등)가 나는" 경로는 완전히 다른 코드 경로
(GlobalExceptionHandler)를 타는데 그건 그대로 방치됨.

--- 재발 (2026-08-27, 90b0ef2) — 왜 3주 뒤 같은 증상이 다시 나왔나 ---
발견 경위: 백엔드 변경분을 실제로 디버깅하며 검수하던 중 GlobalExceptionHandler를 열어보니,
ResponseStatusException 핸들러 바로 위에 "여기 안 걸리면 /login으로 302 나간다"고 설명하는
주석이 이미 있었는데, 정작 그 주석이 경고하는 두 케이스
(MethodArgumentNotValidException, 그 외 미처리 Exception 전체)는 핸들러 자체가 없었다.
영향 범위: grep으로 @Valid를 쓰는 컨트롤러를 전수 확인 — 회원가입/로그인/장바구니/주문/결제
등 11개 파일에 걸친 19개 엔드포인트가 이 미처리 경로에 노출. 즉 이 중 하나라도 빈 값/형식
오류로 검증에 걸리면, 프론트는 필드별 에러 대신 크래시를 겪는 상태가 1차 수정(8/7) 이후
3주 가까이 방치돼 있었다.
재발 이유: 1차 수정은 "미인증 요청"이라는 진입점 하나만 막았을 뿐, "인증된 사용자의 요청이
컨트롤러 안에서 예외를 던지는" 케이스는 다른 코드 경로를 탄다는 걸 그때는 일반화하지
못했다 — 같은 겉증상(axios가 HTML을 받아 크래시)이 서로 다른 원인 경로 두 개에서 나올 수
있다는 게 핵심 교훈.
해결: GlobalExceptionHandler에 두 핸들러 추가.
  - MethodArgumentNotValidException → {"<field>": message} (기존 FieldValidationException과
    동일 관례, Register.jsx가 실제로 기대하는 포맷)
  - 그 외 모든 미처리 Exception → 500 JSON, 스택트레이스는 서버 로그에만


================================================================================
2. Trade-off — 왜 이 방식을 선택했나
================================================================================

[선택 1] authenticationEntryPoint() 전체 교체  vs  defaultAuthenticationEntryPointFor +
         AntPathRequestMatcher("/api/**")로 범위 한정
  → 후자를 선택. 전체를 REST 전용 401 JSON으로 덮으면 코드는 더 짧아지지만,
    oauth2Login()이 내부적으로 등록하는 자기 진입점(/oauth2/authorization/**,
    콜백 처리 등 실제 브라우저 리다이렉트가 필요한 논-API 플로우)까지 같이 사라진다.
    소셜 로그인 자체가 여러 단계의 302 리다이렉트로 동작하는 플로우이기 때문에, 그
    경로까지 401 JSON으로 바꾸면 로그인 자체가 깨진다. 매처로 /api/**만 좁히는 쪽이
    코드 몇 줄 더 들지만 "REST API는 JSON, OAuth2 플로우는 그대로"를 동시에 만족한다.

[선택 2] @Valid 에러 전용 새 응답 포맷 설계  vs  기존 FieldValidationException과
         동일한 {"<field>": message} 재사용
  → 후자를 선택. 새 포맷을 설계하면 이론적으로 더 풍부한 정보(에러 코드, 여러 필드의
    복수 에러 등)를 담을 수 있지만, 프론트(Register.jsx)가 이미 err.response.data.<field>
    로 읽는 관례에 맞춰져 있다. 백엔드가 새 모양을 내려주면 프론트도 같이 고쳐야 하는데
    그건 이번 수정의 범위 밖이다 — CLAUDE.md의 "에러 응답 모양이 프론트 기대와 맞는가"
    체크리스트 항목이 바로 이 판단을 명문화한 것.

[선택 3] 미처리 Exception을 그대로 둔다(빠른 실패, 스택트레이스 그대로 노출)  vs
         catch-all 핸들러로 감싸 500 JSON + 서버 로그로만 스택트레이스 기록
  → 후자를 선택. "그대로 둔다"는 사실 지금까지의 상태(무대응)와 같고, 이게 바로
    이번 사건의 원인이었다. 감싸는 쪽을 선택하되, 클라이언트에는 원인을 노출하지 않고
    (정보 노출 방지) 서버 로그에는 전체 스택트레이스를 남겨(디버깅 가능성 유지) 두
    요구사항을 동시에 만족시켰다.

4. Post-mortem — 재발 방지로 실제 반영된 것 / 아직 안 된 것
================================================================================

실제로 반영됨:
➡️ 코드: 위 3장 표대로 미인증(8/7) + 컨트롤러 예외(8/27) 두 경로 모두 JSON으로 막음.
➡️ 프로세스: CLAUDE.md에 "백엔드 변경 시 자체 검수 체크리스트" 신설 — "새 예외 타입을
   던지는 코드를 추가했다면 GlobalExceptionHandler에 걸리는지 확인"을 명문화. 이번
   재발의 근본 원인이 "체크리스트 없이 각자 판단에 맡겨져 있던 것"이었다는 점에서,
   코드 수정 1건으로 끝내지 않고 재발 방지를 프로세스 단으로 옮긴 대응.
➡️ 문서: GlobalExceptionHandler 안에 "여기 안 걸리면 왜 302가 나는지"를 설명하는 주석을
   각 핸들러 위에 남김 — 실제로 1차 수정 때 남긴 주석이 2차 수정을 촉발한 단서였다
   (주석이 경고하는 케이스 자체가 코드에 없다는 걸 검수 중 발견).

⚠️ 아직 안 됨 (이 케이스 스터디를 쓰며 코드로 직접 확인, 수정은 하지 않음 — 사용자 판단 필요):
➡️ 회귀 테스트 부재: GlobalExceptionHandler를 직접 겨냥한 테스트가 0개다
   (src/test/java 전체에 Exception/GlobalExceptionHandler 관련 테스트 없음, 유일한
   security 테스트는 JwtTokenProviderTest 뿐). 즉 "MethodArgumentNotValidException이나
   임의의 RuntimeException을 던지는 요청이 302가 아니라 4xx/5xx JSON을 받는다"는 지금의
   보장은 순전히 코드 리뷰에 의존한다 — 누군가 이 핸들러 순서를 건드리거나 새
   ExceptionHandler를 잘못된 우선순위로 추가해도 테스트는 그린으로 남는다. 같은 유형의
   재발(3번째)을 코드가 아니라 사람이 우연히 발견하는 패턴이 반복될 위험이 가장 크다.
   → 제안: @WebMvcTest 또는 MockMvc 기반으로 "인증 없이 /api/** 호출 시 상태코드가
   302가 아니다", "@Valid 실패 시 {필드: 메시지} 바디를 받는다", "컨트롤러가 임의
   RuntimeException을 던지면 500 JSON을 받는다(302 아님)" 세 케이스만 고정해도
   회귀는 잡힌다.
➡️ 설정 드리프트 계열(같은 3개월 회고의 1장, 별개 원인)과 마찬가지로, 이 저장소는
